Status: explicit software integration and actual Linux fixtures, awaiting the

## Scope and original inputs

`run_native_trusted_attempt` accepts an optional original
`NativeGuardianCustodyRequest`. The default remains `None`, preserving the
original direct guardian. The opt-in requires Linux FD-bound execution and an
original trusted `registered_observer`; a public worker packet does not create
the request. The caller supplies a live original sealed receiver image, a held
private directory chain and its matching original absolute path, plus original
context, native launch and profile digests. The original sealed bootstrap image
comes from the existing live executable-pair owner registry. A copied pair or
numeric FD cannot manufacture that owner.

Preflight compares the original native launch and current private directory
before consuming an attestation. When the native process is still gated, the
explicit request starts the existing independent receiver with the original
bootstrap owner, exact process, pipes and original absolute deadline. Existing
readiness handling retains its original owner on startup failure. No retry,
new deadline, account provisioning, host interpreter or automatic attestation is
added. The bootstrap and receiver original creating contexts remain caller-owned.

## Pairing order before the gate

Independent durable R still establishes only receiver readiness. It does not mean
the original native execution registration has been published or paired.

1. Publish the original native registration and handoff, retaining the original
   creator FD identities through the existing publisher.
2. Build the original detached `NativeTrustedRegisteredContext` after its existing
   fresh bytes, creator inode, original lock, native grant and deadline checks.
3. Compare its exact native launch, bootstrap image and original attempt deadline
   with the existing receiver reference. Pair the registration/handoff digests,
   original creator pins, lock identity and deadline/binding digests with that
   original receiver reference in one create-only private record.
4. Keep the record's actual creating FD through write, file fsync, directory fsync,
   named-inode comparisons and readback. Retain partial failures. A current stat
   or reopen is used only to compare the creator pin, never to create it.
5. Deliver `GuardianNativeRegistrationReference` through the original request's
   `reference` property. Reobserve the original native context before calling the
   existing trusted observer, which can independently persist that reference.
6. After the observer returns, repeat existing native freshness checks and verify
   the original receiver and paired record again. Only then execute the original
   gate write. Same bytes under a replacement inode, observer failure, missing
   readback or expired original deadline refuses the gate.

The detached context's fields and historical restart wire remain unchanged.
The new record contains no PID, PGID, nonce, key, live FD or process handle.
Existing registration/handoff digests can transitively commit native process
identity, but this record cannot reconstruct or signal it.

## Reference custody and read-only restart

The exact creator-delivered reference includes original receiver bytes, paired
record bytes and creator pin, and its original private directory. The trusted
installation must independently retain these original bytes before allowing the
observer to return. There is no current-record discovery constructor, automatic
retention, or claim that returning the reference proves independent custody.
The existing installed bridge/vault has not been extended in this slice.

`inspect_registered_native_guardian_custody` requires that independent original
reference, opens its exact private directory chain and compares the original
paired record bytes and creator inode before and after reading the independent
receiver record. A fresh process can perform this read without the old Popen or
FDs. It does not launch, signal, repair, renew a budget or load a current record
as original authority. Current native registration freshness still belongs to
the existing original-native recovery/observer, not this diagnostic reader.

A receiver R whose original acknowledgement was lost does not get paired or
retried. A partial pairing leaves its original file and unknown outcome; replay
refuses. A binding created before a later gate refusal remains a pairing fact,
not proof that the gate was released or the target started.

Native success, publication, cleanup and production admission remain false.
Receiver D/exit0 and abnormal exit78 remain exact-child facts, never whole-group
cleanup proof. Blocking filesystem/fsync operations still have no proven hard
completion bound. Accepted build/runtime, installed accounts, authenticated
independent reference retention, installed worker composition and real hard
disconnect acceptance remain separate requirements.
