# Original owner mailbox: durable reconcile registration

## Problem and scope

The private owner-publication mailbox can enter a native publication transaction without
recording the selected owner's recovery obligation. The explicit registration API and the
ordinary resume fence already exist, but they are not composed with this mailbox lifecycle.

This slice registers the obligation on the original owner before
`run_brs_owner_publication_mailbox` services a request. It covers the private mailbox
composition only. Producer preparation has already happened; this is not registration before
the producer's first execution. The direct private native-dispatch primitive and public BRS
routing do not gain automatic registration from this slice.

Publication success, thread completion and executor shutdown do not prove producer-process
cleanup. Consumption remains an explicit evidence-bearing operation. No terminal facts,
prepared references, ACKs, results or publication permissions are generated by registration.

## Contract

1. `retain_reconcile_obligation()` belongs to the genuine original
   `_BRSLineageCheckpointOwner`. It requires the registered TLS owner, original owner thread,
   existing non-reentrant run lock, original wave/state/channel/handoff/context objects,
   `phase=new`, and no active retention, return receipt or settlement.
2. The current owner/wave head and canonical payload must still be the original handoff's
   captured head/state. The original running run and episode, started native claim, request,
   plan, memory, budget, source, policy and execution control must remain exact. A saved result
   or changed run/episode/claim refuses registration.
3. Reuse `register_brs_selected_obligation` and the existing checkpoint field. Optional original
   run-record/native-claim pins are validation constraints, not a new permit or schema. The
   original run head, running episode head, started claim/request/plan, absent result and
   checkpoint CAS must be checked inside the same SQLite write transaction.
4. The only permitted durable delta is adding this exact selected obligation. Its parent
   capture and original handoff/context bytes never change. Other obligations, intents,
   results, budget, lineage, producer references and run/episode records remain unchanged.
5. Before accepting the returned head, verify it is the direct successor of the captured
   head and that its complete payload equals the original payload plus the exact obligation.
   Recheck original source/control/deadline/producer/channel facts. Only then synchronously
   advance the original state, wave cursor and owner cursor. Reading an arbitrary latest head
   is never a recovery strategy.
6. Full source/configuration/control callbacks run outside the short observation mutex,
   channel condition and SQLite write transaction. The final short observation section may
   check fixed identities and durable readback; it must not execute those callbacks.
   Between append and acceptance, the durable cursor is H1 while local cursors remain H0.
   Validate captured identity, running records, recomputed source/policy/control and producer
   pins directly, then re-read the exact adjacent delta. Do not use a normal live-owner
   check that requires durable H0, or temporarily adopt H1 merely to make that check pass.
7. The method is one shot. An uncertain append, callback, readback or acceptance poisons the
   owner, retains its old local capture and preserves any durable obligation. It never retries,
   removes the obligation, or adopts a later head, even if a write probably succeeded.
8. The mailbox composition validates its exact mailbox/run/episode/handoff/original capture
   against the original owner before registration. Registration must succeed before servicing
   the publication request or invoking the native transaction. Empty mailbox, timeout,
   callback failure and successful publication all retain the obligation.
9. Pin the new owner method and registration/store dependencies in the existing source/policy
   contract. Older or changed policies fail closed. Ordinary resume/drive/finalization fences,
   public native BRS refusal, `production_admission=false` and `online_publication=false`
   remain in force.

## Implementation and validation

The owner implementation and ledger pin checks are one workstream. The mailbox composition and
focused tests are another. Documentation, CI selection and isolated server acceptance form the
integration workstream. No workstream changes the frozen PR123 source.

Use real local waiting-worker fixtures: the runner creates the running episode and the first
gateway invocation creates its native claim before the original owner is constructed. Never
retrofit a claim after a terminal result. Prohibit subprocess/model/evaluator/producer execution.

Cover the exact positive delta, immutable parent capture, second-call refusal, stale or foreign
owner/mailbox, run/episode/claim/result drift at the transaction boundary, append/readback
uncertainty, source/control drift and retained ordinary-resume fence. Check that mailbox
transaction execution observes the already-durable obligation and that publication success does
not consume it. Reuse existing terminal-consume tests rather than weakening their evidence gate.

The inert waiting worker lives until the fixture explicitly releases it in `finally`.
A fixed 90-second event wait must not fabricate worker failure during CPU-heavy validation.
Queue acquisition and cleanup joins remain bounded, and product deadlines/budgets are unchanged.

After integration, freeze one source and run disjoint focused groups in separate own-editable
checkouts on macOS and `5090gpu` Linux. Preserve collection/JUnit/source/import/exit evidence;
run Ruff, compileall and `git diff --check`. Independent review and the required full Actions
matrix remain separate merge gates. Local fixtures do not close real runtime/project/CLI or
automatic terminal-recovery acceptance.
